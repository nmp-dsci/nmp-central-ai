Run DeepSeek Harness from this repo, and log every session. Switch off what it sends DeepSeek by default.

DeepSeek Harness (dsh) is DeepSeek's own open-source coding agent: MIT-licensed, released in August, still a developer preview. It ships a local web UI, a one-shot headless command and a server mode for other tools. It has no official terminal UI, but the community dsh-TUI provides one, and this plan uses it day to day. This repo is already shaped the way dsh reads a project, so the work is three things: install it safely, make it send DeepSeek nothing beyond the model calls, and copy each session into the central MLflow.

How it fits this plan

  • The lockdown still applies. Its own patch says the base rows for telemetry, sandbox and approvals are inherited unchanged, and the home layer outranks it. Its docs also list a third upload: your installed plugin names on every request. The home patch turns that off too.
  • It reads your repo the same way. It switches off dsh's top-level instruction and skill loaders and hands them to its agent preset, as dsh's own web UI does. So AGENTS.md and .agents/skills still load. Phase 0 confirms it in the startup context panel (Ctrl+P).
  • Logging is unchanged. Its patch keeps dsh's shared session files under ~/.dsh/sessions. An older page of its docs mentions SQLite, but the current patch doesn't use it. make dsh-log picks them up.
  • It runs at maximum reasoning effort by default on DeepSeek's route, which means more output tokens per turn. Drop it to high in /model for everyday work.
  • It is third-party code inside the agent, with the same access as dsh. Pin the exact version, and read its changelog before each bump. Its /update would move both versions, so the launcher switches that off.
  • Don't add plugins that promise free models. The most-starred one on GitHub today does exactly that; it would send your code through someone else's servers.

What it is, checked against its repo today

DeepSeek Harness in five facts

From deepseek-ai/deepseek-harness at master (pushed 2026-11-13) and the npm package. Every claim here is cited under Sources.

How you run it

npx @deepseek-ai/dsh web serves a browser UI on 127.0.0.1:3080. dsh --profile headless "task" does one task and exits; add --json for an event stream. --profile acp serves other tools over Agent Client Protocol. For a terminal UI, see above. It needs Node 24.9 or newer; this laptop has 25.8.1.

How it is configured

Configuration is stacked in layers: the shipped bundles, then ~/.dsh/profiles/<p>/cordis.patch.yml, then ~/.dsh/cordis.patch.yml, then --patch files. The home layer outranks the settings page. A patch replaces a row's whole config. Keys saved in the UI go to ~/.dsh/.credentials.yaml.

What it reads from a repo

AGENTS.md and CLAUDE.md from the git root down to the working directory, up to 64 KiB. Before them come ~/.dsh/AGENTS.md and ~/.agents/AGENTS.md. Skills come from <root>/.agents/skills and <root>/.dsh/skills, plus the same folders under your home directory.

What it may do

Edit the workspace, run shell commands, use subagents and search the web. The default is the workspace-write sandbox, asking before risky steps. Its SAFETY.md says it is not security-audited and the sandbox is not isolation. Run it with the least access that works.

Where it writes

One append-only log per session at ~/.dsh/sessions/--<cwd>--/<id>/session.v4.jsonl.zstd. Every message, tool call, tool result and the token usage of each model call is in it. That file is what the logger reads. The format has gone from v0 to v4 since August; v4 is current.

This repo needs no changes for dsh to read it. Commit 7827006 made AGENTS.md the real file and moved the four platform-* skills into .agents/skills/. That is exactly where dsh looks, and make agent-check already enforces the frontmatter it needs (name and description). CLAUDE.md is the one-line @AGENTS.md shim. dsh doesn't follow that import, so it adds one harmless line. The gap: the portfolio-level ~/git/nmp-ai-portfolio/AGENTS.md, which points every sibling at PLATFORM.md, sits above each repo's git root, so dsh never loads it. That is Q6.

The setup

One committed config, one guarded launcher, one logger

Read left to right. Solid accent lines are what runs on every launch. Red dashed lines are the flows the home patch shuts. The logger runs afterwards and never touches DeepSeek.

1 · The home patch

agent/dsh/home.cordis.patch.yml, committed. make dsh-install copies it to ~/.dsh/cordis.patch.yml and refuses to overwrite a copy you have edited unless FORCE=1, the same rule install-agent-context follows. It turns off all three uploads and stores sessions uncompressed.

2 · The launcher

make dsh-tui DIR=… is the one you'll use. make dsh-web (browser) and make dsh-run TASK="…" (one-shot) are there when needed. Each runs the pinned dsh under env -i, with the update switches off. First a guard reads dsh --dump-config, and it refuses to launch if any upload row would be on.

3 · The doctor

make dsh-doctor checks five things: Node is 24.9 or newer, dsh is the pinned version, a key is stored (it checks the credentials file exists without reading it), all three uploads are off, and MLflow is up. It also checks for pnpm, which dsh-TUI needs, and reports any session in a format the logger can't read.

4 · The logger

scripts/dsh_log.py (uv, Ruff, mypy strict, pytest on a fixture) reads only new events and writes them to MLflow as shown below. It skips sessions outside the portfolio and replaces secrets with a placeholder. Each span is cut to 4 KB, and reasoning text is never logged.

What lands in MLflow

A session becomes a run; each turn becomes a trace

The run is the ledger: one row per session to sort by cost or tokens. Each trace is one turn: your message, the model calls and the tool calls made to answer it. Token counts come from the provider usage dsh records on each model call, not an estimate.

How to capture the sessions

Three ways to log, and why the simplest wins for now

A · Read the session logs after each session recommended

Python in this repo reads dsh's session files and writes MLflow runs and traces.

  • Covers dsh-TUI, the web UI and headless equally
  • Adds no code inside the agent
  • Tested with pytest on a committed sample session, like the rest of scripts/
  • Not live: run make dsh-log, or a timer later
  • Depends on dsh's file format, which DeepSeek treats as internal and has changed four times since August. The logger is pinned to v4 and stops with a clear error on anything else

B · A dsh plugin for its telemetry hook

A small Cordis plugin takes the place of the OTel uploader and sends spans to MLflow as the agent works.

  • Live
  • A documented hook, with a de-duplication key and a redaction step
  • TypeScript and pnpm in a Python repo
  • The plugin API is a developer preview too
  • A bug in it runs inside the agent process

C · Wrap headless runs only

dsh --profile headless --json into a trace.

  • A few dozen lines
  • Misses every dsh-TUI session, which is nearly all of your use

If dsh changes its file format often enough to hurt, B is the way out. It turns the same session events into the same MLflow shape, so the runs and traces don't change.

What could go wrong

Risks and what covers each one

RiskCovered by
An upgrade turns an upload back onfor example by renaming a row so the home patch no longer matches it The guard runs before every launch, reads the composed config and refuses to start. Upgrades are deliberate: bump DSH_VERSION, then run make dsh-doctor.
Breaking changes in a developer preview dsh and dsh-TUI are pinned to exact versions. The logger handles only session format v4 and refuses others with a clear message.
The agent damages filesSAFETY.md: not audited; the sandbox is not isolation workspace-write with approval prompts, never danger-full-access. Only in git repos, so every change can be reverted. You push, not the agent.
/update moves the pinsit upgrades dsh-TUI and dsh together The launcher sets DSH_TUI_UPDATE_ENGINE=0 and DSH_TUI_UPDATE_LAUNCHER=0, and the guard checks the versions before each launch. Upgrades go through step 9.
Full-access mode is one key awayShift+Tab in the TUI Phase 0 checks whether the mode cycle can leave it out. If it can't, it's a habit: stay in default or plan mode.
Third-party code inside the agentdsh-TUI, and any plugin you add later dsh-TUI is pinned to an exact version and bumped only after reading its changelog. No other plugins without a look at their source, and none that offer free models.
A secret reaches DeepSeekthe agent reads a .env Keys are kept out of its environment with env -i. Use it only in portfolio repos (Q3). Phase 0 checks whether the sandbox can block reading .env*; if it can't, add a rule in AGENTS.md, which is weaker.
A secret or client data reaches MLflow Only portfolio repos are logged. Values found in ~/.env and common key shapes are replaced with a placeholder, and credential files are withheld. The tests plant fake secrets in the sample and fail if any reach a span. MLflow stays on localhost.
Trace volumeplatform rule 4 Spans are cut to 4 KB, no reasoning text is logged, and one trace per turn rather than per event.
Unexpected spend Cost is a run metric, so a costly session stands out in MLflow. dsh-TUI defaults to maximum reasoning; step 6 lowers it. Flash is a quarter of the V4-Pro price (Q5).
