2 · Target shape

One cluster, one database per project, roles owned by the registry

The question this figure answers: after M3, where does each project's data live and how does each process reach it?

Why database-per-project, not schema-per-project

s00 wrote "per-project schemas on the same Postgres". The survey changed the answer: data-qa already is four schemas (app, raw, staging, marts) with 40 Alembic versions, a dbt project and RLS functions that reference app.… by name. Folding it into a shared database means renaming every schema across all of that. A database per project keeps every sibling's internals byte-for-byte, gives per-project pg_dump / pg_restore, per-project extensions, and a clean AWS story (RDS hosts many databases in one instance). DAB's single schema simply lives inside database dab. Nothing needs cross-project joins.

What the registry owns from now on

  • Database names and role names — the only cluster-global namespace, so the registry is the only place they are declared and db_init refuses a duplicate.
  • Extensions — created by the platform superuser once per database, before any project SQL runs.
  • The migrate and smoke commands — like MLflow's smoke, both zero-LLM, run by make check.
  • Nothing inside a database — schemas, tables, grants and RLS stay the project's business, in the project's repo.

4 · Platform primitives — M3.0, built once in nmp-central-ai

The registry grows a database block; four scripts and six make targets act on it

Same pattern as M1: the registry is the source of truth, a script makes reality match it idempotently, a checker proves it, and PLATFORM.md + the plugin tell agents how to use it.

registry/projects.yaml — new block per project

platform:
  postgres_uri: postgresql://localhost:5432      # host
  postgres_compose: postgresql://postgres:5432   # in-network

projects:
  - id: P5
    name: data-qa-agent
    path: ../data-qa-agent
    mlflow: { … unchanged … }
    database:
      name: dataqa                             # D13: one database per project
      roles: [app_user, agent_ro, admin_ro]   # D15: grandfathered; cluster-global, so declared here
      extensions: [vector, pgcrypto]
      env:                                     # what the project reads
        ADMIN_DATABASE_URL: superuser          # D16: the cluster superuser (nmp)
        DATABASE_URL: app_user
        AGENT_RO_DATABASE_URL: agent_ro
        ADMIN_RO_DATABASE_URL: admin_ro
      migrate: make -C ../data-qa-agent migrate
      smoke: make -C ../data-qa-agent db-smoke    # zero-LLM
      aws: false                                  # D19: no project databases in AWS

  - id: P6
    name: dataagentbench
    database:
      name: dab
      roles: [dab_owner, dab_agent]
      extensions: [vector]
      env: { DATABASE_URL: dab_owner, AGENT_DATABASE_URL: dab_agent, PG_SUPERUSER_URL: superuser }
      migrate: make -C ../DataAgentBench db-roles   # runs roles.sql as the superuser, unchanged
      smoke: make -C ../DataAgentBench db-smoke
      aws: false

What each piece does

PieceBehaviour
scripts/db_init.pyFor every project with a database block: CREATE ROLE … LOGIN (password = role name locally, <ROLE>_PASSWORD env overrides), CREATE DATABASE (owned by the superuser, D16), CREATE EXTENSION inside it. Idempotent; refuses if two projects declare the same role or database. Renders SQL (unit-testable) and applies it with psql through docker compose exec -T postgres (or a given superuser URL for AWS). Writes .db-urls.env (gitignored) with one URL per env: key, host localhost; superuser resolves to nmp. Replaces services/postgres/init/01-mlflow.sh, which only ever ran on an empty volume.
scripts/check_databases.pyOne row per project: connect as the superuser and as each role, assert extensions present, run the project's smoke with the URLs exported. make check runs it after the MLflow checker; --only P6 works the same way.
make db-init · db-urls · db-checkProvision · print the URLs (and where the project should paste them) · verify.
make db-backup DB=dab · db-restore DB=dab FILE=…pg_dump -Fc to backups/<db>-<utc>.dump (gitignored) and the matching pg_restore -j4 --no-owner (everything ends up owned by nmp, as it is owned by the local superuser today). The migration playbooks below use these against the old containers too (SRC=container).
docker-compose.ymlPostgres flags from env (D17); nothing else changes. The MLflow database becomes a registry entry (id: PLATFORM) so the same script owns it.
PLATFORM.md + pluginNew "Postgres" table (URLs, rule: one database per project, roles from the registry, the superuser only for migrations and only in your own database, never a local db service, reset = drop your own schemas) and rule 7. Skill platform-db added to nmp-platform with an eval case ("add a table to my project" → must not create a compose postgres, must use the registry URL).
CIstack job adds make db-init && make db-check ARGS="--only PLATFORM"; tests/test_db_init.py renders SQL for a fixture registry and asserts the statements and the duplicate-role refusal.
The one coupling stays one env var per URL. A sibling never imports the platform. It reads DATABASE_URL (and friends) exactly as it does now; only the default value and the hostname change. Validation and CI use a throwaway server with the same hostname (D12, D18).
5 · Moving data — the same six steps for every project

Dump from the old container, restore into the registry-made database, prove, cut over, delete the old one

1 · freeze

Stop writers, keep the old server up

  • project's app containers down; its db stays up
  • make -C ../nmp-central-ai db-init creates the target
2 · dump

From the old container

  • docker exec <old> pg_dump -Fc -U <su> <db> > backups/…
  • size check vs pg_database_size
3 · restore

Into the central database

  • pg_restore -j4 --no-owner -d <db> as nmp
  • extensions already exist → --no-comments, ignore "already exists"
4 · prove

Counts match, roles work

  • per-schema table counts and pg_total_relation_size within 2 %
  • project's db-smoke as each role (RLS still hides rows for user2, agent role still read-only)
5 · cut over

Change the defaults, delete the service

  • URLs → postgres/localhost:5432
  • compose db service + depends_on removed, network joined
  • make up, full smoke/e2e
6 · delete

Old server gone, port freed

  • step 4 proved the central copy complete, so the old container and its volume are removed right away (reviewer decision: the data is easy to recreate from source anyway)
  • the step-2 dump file stays in backups/ as the safety net

Rollback at any step before 6: put the old default back and docker compose up db. Nothing in steps 1–5 writes to the old volume. After 6, rollback is make db-restore from the dump, or a re-ingest from source.

9 · Out of scope, on purpose

Kept where they are

ConvFinQA .traces/traces.db

Embedded SQLite behind a server-free demo image. A Postgres port would force the demo to carry a database or lose the Traces page. Revisit only if a second project needs a shared turn store.

DuckDB (value-invest, productivity-tracker)

Columnar, file-based, analytical. Different engine, different job; the s00 guardrail (duplication ≥ 2 and its own plan) is not met for a shared OLAP service.

Neo4j (transcript-rag)

Graph database; single consumer. Stays project-local.

v2v-prod-agent, Databricks projects

Excluded from the platform in s00.

AWS databases

D19: the AWS stack is a demo with no project databases. data-qa's own Terraform keeps its Aurora untouched; M2/M5 decide what the demo shows.

Connection pooling

Four projects, one laptop: not needed. PgBouncer enters the catalogue when a second concurrent-heavy service appears.
