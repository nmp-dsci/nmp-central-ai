1 · Validation

Is centralising the right move? Yes, with two guardrails.

The case is not theoretical. The compose files in the sibling repos already narrate the problem in their own comments.

Evidence for

  • Port allocation is collision-driven. data-qa's compose says it moved to 5500 "because ConvFinQA's MLflow owns 5000 on this machine"; DABStep took 5600, tau2 5601. Four stores, no shared registry, no cross-project comparison.
  • Non-portable state has already crept in. ConvFinQA's compose bind-mounts an absolute laptop path so old runs still show artifacts. That file cannot run on another machine. ConvFinQA-agent/docker-compose.yml:61
  • Deprecated store still in use. transcript-rag-agent defaults to file:.yt-agent/mlruns, which ConvFinQA's own code comments call deprecated as of Feb 2026.
  • Accidental local stores. databricks-propertyiq has a stray mlflow.db and mlruns/ despite pointing at Databricks, the exact failure databricks-sa-coding warns about in scripts/deploy_endpoint.py:41.
  • The same tracking module is copy-pasted. DABStep-loop and tau2-loop carry byte-similar tracking/mlflow_log.py, snapshot.py, registry.py.
  • It is what you told the portfolio site you do. nmp-dsci.github.io promises "per-request traces and cost caps" across four live systems. A platform repo is the credible backing for that claim.

Guardrails, or this becomes a liability

  • Keep the coupling to one env var. Nobody clones a single project standalone in practice, so this costs nothing: MLFLOW_TRACKING_URI is the only contract, and platform code stays out of each project's hot path in M1. Agreed in review.
  • Local mirrors AWS in shape, not just in URL. Postgres backend and S3-compatible artifacts from day one (MinIO locally, RDS + S3 in AWS). Confirmed in review: this is a production-systems portfolio, so parity is the point. No longer an open decision.
  • Databricks projects are out of scope. databricks-propertyiq and databricks-sa-coding use Databricks-managed MLflow by design. Excluded, not a priority; no cleanup work planned.
The enterprise analogy holds. This is a platform team with an internal service catalogue, onboarding runbook, and a per-project registry. The discipline you want is: a project declares what it needs in one YAML entry; it never spins up its own copy.

3 · Target

One stack, one URL, one env var.

The central repo runs Postgres, MinIO and one MLflow server on a named Docker network. Projects reach it either from the host (http://localhost:5000) or, if they run in compose, by joining the nmp-central network and using http://mlflow:5000. Nothing else about a project changes in M1. Backend store and artifact layout are settled: Postgres and S3-compatible, locally and in AWS.

Conventions the platform imposes

experiment
<project>/<purpose>, e.g. convfinqa/evals, dabstep-loop/loop. data-qa already does this (data-qa/evals). Existing flat names are kept as aliases in M1 to avoid churn; renaming is a follow-up.
tags
project, git_sha, env (local / aws), billing. Set by each project's existing tracking module; a shared helper comes later (D3 decided: env var only in M1).
ids
make mlflow-init in the central repo creates every experiment from registry/projects.yaml idempotently and prints the numeric ids data-qa's OTLP header needs.
ports
Central MLflow on 5000, Postgres on 5432, MinIO on 9000 / 9001. Sibling projects delete their own mlflow services and stop squatting 5500 / 5600 / 5601.
fallback
If the server is unreachable a project's make eval should fail fast with a message that names make -C ../nmp-central-ai up, not silently create a local sqlite store.

Local compose, in short

services:
  postgres:  pgvector/pgvector:pg16    # 5432, volume pgdata
  minio:     minio/minio               # 9000 api, 9001 console
  mlflow:    build: services/mlflow    # 5000
    command: mlflow server --host 0.0.0.0 --port 5000
      --backend-store-uri postgresql://mlflow:***@postgres/mlflow
      --artifacts-destination s3://mlflow-artifacts
      --serve-artifacts
    environment: MLFLOW_S3_ENDPOINT_URL=http://minio:9000
    depends_on: postgres (healthy), minio-init (bucket)
networks:
  default: { name: nmp-central }      # external-joinable by siblings

Profiles reserved for later milestones: --profile gateway (LiteLLM), --profile metrics (Prometheus + Grafana, lifted from data-qa).

Public-repo checklist

  • gh repo create nmp-dsci/nmp-central-ai --public --source . --push after the first commit; add the no-mistakes mirror remote.
  • No real secret ever committed: .env.example carries names and local-only defaults (MinIO minioadmin is fine locally, rotated in AWS).
  • MLflow basic-auth credentials and the RDS password live in AWS Secrets Manager; Terraform reads them, never writes them to state in plain text where avoidable.
  • Terraform state in the bootstrap S3 bucket, GitHub Actions authenticates with OIDC, no long-lived AWS keys in repo secrets. Same as your six sibling stacks.
  • Account id and SSO URL never appear in code; region ap-southeast-2 is a variable.
  • Bulk data and volumes are gitignored; .lavish/ is tracked (workspace rule).
  • README states the standalone rule so a reader knows sibling projects still run without this repo.

B · ECS Express Mode + RDS + S3 upgrade path

AWS's named successor to App Runner. Fargate task, shared ALB, auto HTTPS domain, deployed with the same Terraform + GitHub OIDC pattern you already use. Matches MLflow's reference architecture.

  • Smallest Fargate size is enough for a demo with no live data.
  • The shared ALB becomes the front door for every later central service and for the six sibling demos that must leave App Runner anyway.
  • Sleep and wake are two Make targets.
≈ USD 46 / month always on · ≈ 23 asleep. Move here only if the demo needs more than one box.

E · One Graviton EC2 running the compose file decided

A t4g.small with Docker, running the same docker-compose.yml as your laptop plus Caddy for HTTPS, pointed at RDS and real S3.

  • Cheapest credible option and the purest dev/prod parity story: the demo runs the file you develop against.
  • Later services are extra compose services plus a Caddy route; no ALB to pay for.
  • You patch a VM: Amazon Linux 2023 with SSM, unattended security updates, and a rebuild-from-Terraform runbook so it never has to be nursed.
≈ USD 35 / month always on (EC2 ≈ 16, RDS ≈ 18, S3 ≈ 1) · ≈ 6 stopped.

What the platform-mlflow skill teaches

  • Trigger words: "log this run", "trace", "compare runs", "experiment", "prompt registry", "which model is in production".
  • Log correctly: experiment naming, required tags, when to use mlflow.start_span vs framework autolog, artifact size limits.
  • Query correctly: search_runs / search_traces snippets against the central server; how to read data-qa's OTLP header setup.
  • Do not: start a server, create a sqlite store, hardcode an experiment id, log secrets or PII.
  • Verified with claude plugin eval cases: "log an eval run from tau2-loop", "find yesterday's slowest trace in data-qa".
